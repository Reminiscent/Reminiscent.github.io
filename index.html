Replacing GEQO with GOO + rollout + LinDP

What makes a join order algorithm “better”, and where the evidence is.

0 · Summary

When the number of FROM items reaches geqo_threshold (default 12), PostgreSQL switches from exhaustive dynamic programming (DP) to the genetic algorithm GEQO. This note evaluates a deterministic alternative: the greedy algorithm GOO, extended with two improvements, rollout and LinDP (“the new algorithm” below). To replace GEQO, the new algorithm must be no worse in five respects. Apart from Section 8, all execution data come from the JOB benchmark (the 33 queries with ≥12 relations in JOB and JOB-Complex):

  • Benchmarks: JOB[1] and JOB-Complex[2] (IMDB data). They are the most widely used join order benchmarks, and their queries are small enough to run with true cardinalities. -O2 build; 1 warm-up + 3 measured runs per query and algorithm.
  • Wider queries (44 queries with 12–51 relations on MusicBrainz[3]) are for reference only; see Section 8.
  • “Execution time” always excludes planning time (it is the Execution Time reported by PostgreSQL); planning time is compared separately in Section 5. Only where “total time” is stated explicitly do we mean planning + execution. Experimental setup

1 · How to judge a join order algorithm

The planner optimizes Total Cost, not execution time

This section first explains how to compare two join order algorithms, then checks the method against JOB data. A query goes through two phases. During planning, only estimated row counts are available; the planner computes the Total Cost of each candidate plan from these estimates, and the join order algorithm searches for the candidate with the lowest Total Cost. Execution time is known only after the plan runs on the actual rows.

So if the row estimates are wrong, the plan with the lowest Total Cost can run slowly, regardless of how good the search is. Plan quality must still be judged by execution time. Here execution time excludes planning time: it reflects only the quality of the chosen plan; how long planning took is a separate question, covered in Section 5. Execution time has to be examined under two conditions:

ConditionMeaningQuestion answered
True cardinalitiesEvery intermediate result's row count is replaced by its actual count, then the planner plansWith accurate inputs, how good is the plan the search finds?
Estimated cardinalitiesPostgreSQL's normal behavior: row counts estimated from statistics collected by ANALYZEWhat do users get today?

Estimates depend on statistics, and ANALYZE samples, so each ANALYZE of the same data produces slightly different statistics. We therefore ran 5 independent ANALYZEs on the same data, producing 5 statistics snapshots, and measured everything on each. Every estimated-cardinality chart below can switch between snapshots; the default is snapshot 3, whose execution-time geometric-mean ratio is the median of the five.

A counter-check with DP

DP is optimal under the cost model. If per-query speed were mainly determined by the search, DP should clearly beat GEQO on execution time.

    Even the theoretically best search algorithm beats GEQO on fewer than half the queries under estimated cardinalities (12–16 of 33 across the 5 snapshots); with true cardinalities, DP is faster on all 33. Per-query speed is therefore determined mainly by estimation error. This does not make execution time unimportant; it means a single query is not enough, and we must look at:

    • The distribution: the geometric mean of execution time, and how many queries each side makes more than 2× slower (the new algorithm slower than GEQO, and GEQO slower than the new algorithm);
    • Several statistics snapshots, so that a conclusion does not hinge on one ANALYZE;
    • Both conditions separately: true cardinalities test the search, estimated cardinalities reflect what users see.

    The baseline is always GEQO; DP is a reference only. GEQO runs with all default settings, for these reasons:

    • geqo_threshold (default 12) sets the relation count at which GEQO takes over, which is also the scope of this comparison: all queries with ≥12 relations.
    • geqo_effort (default 5, range 1–10) sets the pool size and number of generations, trading planning time for plan quality. At the default setting, GEQO's planning time on JOB is already about 3× that of the new algorithm (Section 5); raising it only makes GEQO plan more slowly, and lowering it gives up plan quality, so neither direction changes the conclusions. geqo_pool_size and geqo_generations are derived from it by default, and geqo_selection_bias stays at its default.
    • geqo_seed (default 0) only selects which random path the search takes. A different seed yields another equally random set of plans: some queries improve, others get worse; no seed is systematically better, and there is no way to pick a good seed for a query in advance. Keeping the default makes GEQO produce the same plans every time, so the comparison is reproducible; the variation across seeds is the same kind of instability as the variation across statistics snapshots in Section 4.

    2 · Algorithm: two improvements on GOO

    The new algorithm is built on GOO. Rollout and LinDP each improve GOO, addressing one of its two weaknesses. The example below uses 5 tables. To keep the mechanism visible, it uses the simplest possible cost: the sum of all intermediate result sizes. The real implementation uses PostgreSQL's own path costs.

    • Nodes are tables with their row counts; edges carry join selectivities.

    The example only illustrates the mechanism: here each step improves on the previous one, and LinDP happens to reach DP's optimum. On real queries, not every step is guaranteed to improve.

    Base: GOO

    GOO (Greedy Operator Ordering, Fegaras 1998[4]) merges bottom-up: at each step, among all pairs of groups that can be joined, it merges the pair with the best score, until one group remains. This implementation runs it once for each of two scores: smallest result size and lowest cost. It is deterministic and cheap, but has two weaknesses:

    • It looks only one step ahead. Each step compares only that step's results, and a merge cannot be undone. The smallest join now may force larger joins later.
    • The parenthesization is fixed. Once the order of merges is decided, so is the way tables are associated.

    Improvement 1: rollout, for the one-step lookahead

    Rollout comes from approximate dynamic programming (Bertsekas et al., 1997[5]). Each step still commits exactly one join; only the choice changes: take the top two candidates by GOO score and roll each out, that is, assume it is committed and finish the plan with plain GOO; compare the two complete plans, commit the better step, and discard the rest of both rollouts. Each step does two rollouts; joins evaluated during rollouts are cached and reused, so the actual cost is far below “2n × GOO” (Section 5 has measured counts).

    Why it helps: GOO looks only at the current step, implicitly assuming later cost does not depend on it. Rollout scores each candidate by “the complete cost of committing this step and finishing with GOO”, so the ignored consequences are counted. In approximate dynamic programming this is one step of policy improvement.

    Why it is never worse than GOO: at step 1, GOO's first choice is one of the two rolled out, and its rollout is exactly the plain GOO plan. At every later step, continuing with GOO's first choice is exactly the rollout path chosen at the previous step, so the best available complete plan can only improve.

    Improvement 2: LinDP, for the fixed parenthesization

    LinDP is linearized DP (Neumann and Radke, SIGMOD 2018[6]). DP searches two things at once: the order of tables (commutativity) and the parenthesization (associativity); the first produces 2n subsets, which is why DP is infeasible for large queries. LinDP fixes a leaf order with a good heuristic, gives up reordering and keeps only associativity: it runs DP only over contiguous intervals of that order, O(n²) intervals with O(n) split points each, and finds the best parenthesization for that order.

    So LinDP is only as good as its order. The original paper derives the order with IKKBZ; we use the rollout result: every subtree of the rollout plan is a contiguous run in its leaf order, so the good subplans found by GOO and rollout are preserved in LinDP, and LinDP adds parenthesizations GOO never tried (such as D⋈A in the example). Never worse than rollout: the rollout tree is itself one parenthesization of this order, and LinDP takes the best of all of them.

    Why not derive the order with IKKBZ, as the paper does. We keep LinDP's interval DP unchanged and only replace how the order is produced. IKKBZ yields the optimal left-deep order under two conditions: an acyclic join graph, and a cost function with the ASI property (such as Cout, the sum of intermediate result sizes). The paper runs IKKBZ on a minimum spanning tree of the join graph and uses Cout in its experiments. In PostgreSQL both conditions hold only approximately:

    • Join graphs are often cyclic. Equivalence classes derive additional join clauses; IKKBZ can only order a spanning tree, so the clauses that are cut do not influence the order.
    • The cost model does not have ASI. PostgreSQL's path costs depend on indexes and physical operators, so ordering must use a proxy such as Cout, which differs from the Total Cost used to compare the final plans.

    We implemented an IKKBZ + LinDP variant; its actual execution results on JOB were not good enough, so we use the rollout result as the order instead. This may also be due to our implementation (for example the proxy cost used for ordering, or the choice of spanning tree), so it should not be read as evidence that IKKBZ is unsuitable.

    How the three fit together

    GOO with rollout runs once for each of the two scores; LinDP runs once, on the order of the rollout result with the lower Total Cost (LinDP is more expensive, so it runs only once). The complete plans from plain GOO, rollout and LinDP are all kept as candidates, and the cheapest by Total Cost wins. The result is therefore never worse than GOO and never worse than rollout; it is not guaranteed to beat LinDP over other orders, a trade-off made to bound planning time.

          4 · Robustness

          Why estimation errors cause extreme regressions

          Underestimates are common, yet most queries do not regress because of them. Turning one into an order-of-magnitude regression takes four things happening in sequence:

          Link 1  Underestimation: after many joins, an intermediate result of tens of thousands of rows is estimated at tens of rows, or even 1
          Link 2  An index nested loop is chosen: with a small outer estimate, the planner has each outer row look up the inner table's index once (a “probe”)
          Link 3  Total Cost cannot tell plans apart: every plan's outer side is estimated small, the costs are nearly equal, and which one wins is close to arbitrary
          Link 4  Execution amplifies it: the number of probes equals the actual outer row count; if the chosen order puts the underestimated large result on the outer side, it probes tens of thousands of times more, and that is mostly where the extra time goes

          We first walk through one real query (JOB 28b, the one the new algorithm runs about 9× slower in Section 3), then test each link on all plans.

In 28b, 86,022 rows are estimated as 39. Estimates are clamped at 1 row, so an estimate of 1 means the underestimate has bottomed out: among joins of 13 or more tables, 94% are estimated at 1 row, and 71% of those actually have more than 100 rows.

          • Estimated cardinalities; all plans of the 5 snapshots and three algorithms. Each bar is a group of joins (grouped by the number of tables in the join), scaled to 100%. Hover for counts.
          Link 2: an index nested loop is chosen An index nested loop has each outer row look up the inner table's index once, so its cost is roughly “outer rows × one index lookup”. JOB has indexes on all foreign-key columns, so with tens or hundreds of outer rows it is far cheaper than reading the whole inner table into a hash table. The chart below groups all joins by estimated outer row count and shows the share that use a nested loop: 97%–100% when the outer side is estimated at ≤100 rows, only 3%–6% above 10,000 (for outer estimates between 2 and 10,000 rows, 92%–100% of these nested loops have an index scan on the inner side). This link determines how costly an underestimate can be: a hash join reads each table once, so its cost is bounded however large the outer side is; an index nested loop's cost grows linearly with the actual outer row count.

          The smaller the outer estimate, the more often a (index) nested loop is chosen

          • Estimated cardinalities; joins in all plans of the 5 snapshots and three algorithms, grouped by the estimated row count of the outer (driving) side.
          Link 3: Total Cost cannot tell plans apart Every candidate plan's outer side is estimated small, every probe is expected to run only a few times, and so the Total Costs come out close. Of all 112 cases where one of the three algorithms is ≥5× slower than another, in 84 the two plans' Total Costs differ by less than 1%. The planner did not pick the slow plan because it “miscalculated”; to the planner the plans were nearly equally good, and the choice came down to how the search breaks near-ties. The new algorithm, GEQO and DP all pick slow plans this way, just on different queries.

          Over all ≥5× regressions: how far apart the two plans' Total Costs are

          Link 4: execution amplifies it An index nested loop probes the inner index once per actual outer row: if the outer side is an underestimated large result, probes expected to run tens of times run tens of thousands to tens of millions of times. To see directly where the time goes, we re-ran all 73 pairs of ≥5× regressions (14 queries) the same way as the original measurements (1 warm-up + 3 measured runs, median taken) with per-node timing enabled (an EXPLAIN ANALYZE option that records each plan node's own time; the original measurements disabled it to reduce overhead). For 13 of the 14 queries, 87%–100% of the slow plan's extra time is spent on index probes (100% for 28b). The one exception, q17, spends most of it building a hash table over a result estimated at 1 row but actually 44.71 million: the same cause, through a different operator.

          Is this a problem with the new algorithm's search? No. None of the four links depends on the search algorithm: DP shows the same regressions under estimated cardinalities (Section 1), and GEQO's extreme regressions follow the same mechanism, for example JOB-Complex q17 taking 306 s in snapshot 5. With true cardinalities, Total Cost can tell plans apart again: on the same 33 queries, the new algorithm is ≥2× slower than GEQO on 0, and on 28b it picks exactly the plan DP picks.

          The advantage under true cardinalities shows that the new algorithm's search is good; the regressions under estimated cardinalities come from underestimation: it leads the planner to operators whose cost scales with row count (mainly index nested loops), it takes away Total Cost's ability to discriminate, and execution then scales the cost by the actual row count. No static algorithm working from the same estimates can fully avoid such regressions.

          Stability under statistics resampling

          Each ANALYZE samples differently, so the statistics for the same data vary slightly. A good planner should not change its plan drastically when its input changes slightly.           The reason is structural: GEQO's evolutionary trajectory depends on the cost of every candidate, so a tiny cost perturbation changes the whole trajectory; greedy search and DP change a decision only when a perturbation crosses a comparison boundary, so they are piecewise stable. Within a snapshot, across the 4 executions (1 warm-up + 3 measured), none of the three algorithms changed its plan: what is measured here is sensitivity to statistics resampling, not randomness under a fixed seed.

          5 · Planning time

          For JOB (12–17 relations), the new algorithm's median planning time per query is about 6 ms, GEQO's about 21 ms. Wider queries are measured with two public planning workloads. Their tables are tiny (10–200 rows each), so they are used only for planning time, not execution:

          • SQLite select5: the join stress test from SQLite's sqllogictest suite[7]; 732 queries with 4–64 relations, all primary-key/foreign-key joins. The LinDP paper also used it to measure planning time[6].
          • chain, star, snowflake, clique: synthetic workloads from the GPUQO project[8], generated by join graph shape: a chain is a path; a star is one central table joined to all others; a snowflake is a star with further outward layers; a clique has a join clause between every pair of tables and has the largest search space. We use its small-scale variants: chain, star and clique up to 16 relations, snowflake up to 40.

          At 16 relations, DP's planning time depends heavily on the join graph shape: chain and SQLite select5 take about 3 ms, faster than the new algorithm; snowflake about 78 ms, star about 0.94 s; clique exceeded the 8 GB memory limit and did not finish.             6 · Correctness

            A join order decides only the order and method of joins and must not change query results. Method: run the whole PostgreSQL regression suite with geqo_threshold=2, so that nearly every multi-relation query goes through the new algorithm (and do the same with GEQO for comparison), then check whether query results or errors change.

            • New algorithm: no query result changed and no new errors; all differences from the expected output are plan differences shown by EXPLAIN, which is expected when the search algorithm changes.
            • With the default configuration (the new algorithm not forced), the regression suite passes.
            • Failures caused by LATERAL are excluded: both GEQO and the new algorithm have LATERAL dependencies they cannot handle, triggered by different SQL.

            7 · Controllability

            Every heuristic picks badly on some queries, so whether a bad pick can be corrected matters. pg_plan_advice lets users constrain a query's join order (JOIN_ORDER) and other choices without changing the SQL and without disabling a planner capability globally.

            How it works determines which search algorithm it fits better: pg_plan_advice does not generate plans on the planner's behalf; instead, whenever the planner builds a join, it tells the planner whether that join is disallowed. It can therefore only choose among plans the planner would consider anyway.

            New algorithmGEQO
            Basic search actionAt each step, list all legal merges of two groups and pick one pairGenerate a random permutation of the tables and assemble a tree in that order
            How a constraint takes effectMerges that violate the constraint are excluded at that step; the remaining candidates are chosen by the usual rulePermutations that violate the constraint can only be discarded; whether a compliant permutation appears depends on the random process
            ResultAs long as the constraint is itself valid, every step has a compliant candidate, so producing a compliant plan is deterministicWhether a compliant plan is found depends on whether the matching permutation appears in the pool

            The community discussion of pg_plan_advice also noted that join order constraints under GEQO can only act on options the genetic search actually considers. This section is a structural analysis based on how the mechanisms work.

            8 · Reference: wider queries (MusicBrainz)

            The conclusions above all rest on JOB, whose queries have at most 17 relations. Wider queries need another benchmark; this section explains why we use MusicBrainz rather than synthetic data, and what we see on it. This part is for reference only and does not feed into the conclusions above.

            Why not a synthetic benchmark

            The obvious idea is to generate many wide queries over synthetic data. We tried several directions: generating only join graphs and injecting row counts; generating small tables and actually executing; and generating queries by classic shapes (chain, star, snowflake, clique). The problems we ran into fall into three groups:

            • The more controllable the data, the easier the problem. To keep results interpretable, the data is usually uniform and independent, so estimates are mostly accurate. The simplest greedy rule then tends to be near-optimal already and the algorithms are hard to tell apart; the correlations and skewed values that cause regressions on real queries are absent from generated data.
            • Without execution, only Total Cost can be compared. Generating join graphs alone gives no execution time, and Total Cost cannot answer “will users' queries get slower?”; with many relations, the Total Cost differences between plans also shrink below the fuzz factor PostgreSQL uses when comparing paths.
            • With execution, the data size is hard to get right. Small tables run in milliseconds, and measurement noise exceeds the differences between algorithms; large tables are expensive to generate, and their distributions are still artificial.

            Making synthetic data both controllable and as hard as a real workload is a substantial problem in its own right, so we turned to wide queries over real data.

            The MusicBrainz benchmark

            MusicBrainz is a public music metadata database; we use its official full export (the queries touch 81 tables, about 300 million rows, the largest being track with 57.7 million rows). It has no public query workload, so the 44 queries (12–51 relations) are business queries generated by AI from its data model, accepted as long as they meet the general requirements below, with no further manual selection:

            • A clear business question, such as “which works have at least two different composers or lyricists”;
            • Joins follow relationships between entities in the schema (primary/foreign keys, link tables), with no joins that lack business meaning;
            • A non-empty result on the full data, without contriving one, for example by pinning internal IDs;
            • Wide enough: at least 12 relations, within GEQO's range.

            The differences from JOB: the data and queries are larger, but the queries are generated rather than established, and because the queries have many relations over large tables, there is no true-cardinality comparison yet (see below for why). Only GEQO and the new algorithm are compared, using PostgreSQL's native estimates, with a 900 s timeout.

              Execution qualityMetFaster on 33/33 with true cardinalities; with estimated cardinalities, lower total execution time in all 5 snapshots and fewer large regressions than GEQO; the new algorithm also has queries close to 10× slower or worse (about 0.1 s becoming 1–2 s)
              RobustnessMetRegressions come from underestimation: small estimates lead to index nested loops, Total Cost cannot tell plans apart, and execution scales the cost by the actual row count (for 13 of the 14 regressing queries, the extra time is mainly spent on index probes).               These conclusions are based on JOB and JOB-Complex. On the reference MusicBrainz workload (Section 8), the new algorithm is faster on 29 of the 41 queries both completed; timeouts: 1 for the new algorithm, 2 for GEQO; at 36–51 relations, planning takes about 1.3× GEQO's time, which is negligible relative to execution time.

              What we do not claim

              • We do not claim robustness to cardinality estimation errors: no static algorithm working from the same estimates can achieve that.
              • We do not claim that no query regresses; Sections 3 and 4 list the regressions and their causes.
              • We do not claim a new algorithm: GOO, rollout and interval DP are all known ideas; the value is in being deterministic, explainable and cheap, and in integrating with PostgreSQL's cost model and path machinery.

              Limits of the evidence and open questions

              • Scope of the execution evidence. The conclusions rest on JOB and JOB-Complex (12–17 relations). MusicBrainz (12–51 relations) is for reference only: the queries are generated, only one statistics snapshot was measured, and because the queries have many relations over large tables there is no true-cardinality comparison yet, so regressions on wide queries cannot be attributed to estimation error or to the search (Section 8).
              • Planning time at large relation counts. Above about 32 relations, a principled budget or fallback is needed (Section 5).
              • Form of the proposal. What to do outside the supported range (for example, fall back to GEQO, or use GOO with only one of the improvements) is still to be decided.

              Appendix · Method and reproduction

              • Configuration under test: every query that GEQO would plan (FROM items ≥ geqo_threshold) uses the new algorithm instead, with no fallback to GEQO; below the threshold, DP is used as usual. GEQO uses all default settings (geqo_effort=5, geqo_seed=0, geqo_threshold=12).
              • Build: CFLAGS=-O2, ICU; Apple M4 Max, 36 GiB of memory.
              • Session settings: join_collapse_limit=from_collapse_limit=100, max_parallel_workers_per_gather=0, work_mem=1GB, effective_cache_size=8GB; timeout 600 s for JOB, 900 s for MusicBrainz.
              • Measurement: for each query and algorithm, 1 warm-up followed by 3 measured runs. Execution time is the Execution Time reported by EXPLAIN ANALYZE, excluding planning time; planning time is recorded separately.
              • Estimated cardinalities: 5 independent ANALYZEs on JOB, with a full run per snapshot. True cardinalities: a replay cache miss raises an error rather than falling back to the estimate (99/99 coverage).
              • All statistics snapshots, schemas, server settings, the replay cache and plan JSON are saved, so results can be reproduced from the recorded commit and snapshots.
